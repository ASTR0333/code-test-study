# Полнота тестов и оценка корректности кода языковых моделей

Воспроизводимый эксперимент по оценке того, как расширение автоматических тестов меняет долю принятых программ, сгенерированных языковыми моделями.

Материалы к статье **«Влияние полноты тестов на оценку корректности кода языковых моделей»**.
Авторы: Алексей Андреевич Герик и Людмила Владимировна Бунина, МИРЭА — Российский технологический университет, Москва, Россия.

## Что сделано

Выполнена повторная автоматическая проверка **опубликованных архивных решений**. Для каждой из 164 задач HumanEval взято по одному неизменённому файлу двух корпусов EvalPlus:

- `gpt-4-1106-preview_temp_0.0`;
- `code-llama-7b_temp_0.0`.

Названия корпусов и температура 0.0 приведены по исходным архивам. Проверка выполнена на готовых ответах моделей; повторная генерация и восстановление исходных запросов не проводились. Для воспроизведения достаточно Python и NumPy: API-ключи и загрузка весов моделей не требуются.

Основной анализ охватывает 163 задачи на корпус: задача HumanEval/32 исключена одинаково для обеих моделей, поскольку её эталон не проходит собственный критерий невязки. Исключение основано на контрольном прогоне эталона, а не на оценках моделей. Все 164 исходные задачи и все исходные результаты сохранены.

## Основные результаты

| Набор | GPT-4-1106-preview | Code Llama 7B |
|---|---:|---:|
| Базовые тесты | 141/163 (86.50%) | 62/163 (38.04%) |
| Базовые + до 10 дополнительных входов | 138/163 (84.66%) | 57/163 (34.97%) |
| Базовые + до 100 дополнительных входов | 136/163 (83.44%) | 57/163 (34.97%) |
| Базовые + все дополнительные входы | 134/163 (82.21%) | 57/163 (34.97%) |

Дополнительная проверка выявила у GPT-4 **5 несовпадений ответа и 2 превышения времени**, у Code Llama — **3 несовпадения и 2 превышения времени**. Значения вычислены скриптом [`analyze.py`](analyze.py) из журналов выполнения. Базовые тесты соответствуют полю `base_input` HumanEval+ v0.1.10.

Сводные результаты доступны в [`results/analysis/summary.md`](results/analysis/summary.md), показатели по задачам — в [`results/analysis/task_results.csv`](results/analysis/task_results.csv).

## Воспроизведение в Windows

Проверенная среда: **Windows 11, CPython 3.12.14, NumPy 2.3.5**. Результаты, зависящие от времени выполнения, могут отличаться на другой машине.

Установите Git и Python 3.12, затем откройте PowerShell и загрузите проект:

```powershell
git clone https://github.com/ASTR0333/code-test-study.git
cd code-test-study
```

Создайте окружение и установите зависимости:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe test_evaluator.py
```

Для пересчёта включённых в репозиторий измерений выполните:

```powershell
.\.venv\Scripts\python.exe analyze.py
```

Для полного повторного эксперимента выполните контроль эталонов, проверку двух корпусов и расчёт результатов:

```powershell
.\.venv\Scripts\python.exe runner.py --canonical --min-time 1 --jobs 2 --output results/control-replay
.\.venv\Scripts\python.exe runner.py --min-time 10 --jobs 2 --output results/replay
.\.venv\Scripts\python.exe analyze.py --results results/replay --control results/control-replay --out results/replay-analysis
```

Новые результаты сохраняются в `results/replay/`, сводная таблица и CSV — в `results/replay-analysis/`. Эти каталоги исключены из Git через `.gitignore`, поэтому повторный запуск сохраняет исходные опубликованные журналы.

Полный запуск выполняет реальные программы и обычно занимает несколько минут. Используйте только включённый, проверенный по SHA-256 корпус. Ограниченный Python namespace и проверка импорта в стенде не заменяют системную песочницу для произвольного чужого кода. Для запуска нового непроверенного корпуса используйте отдельный контейнер или виртуальную машину. В данном эксперименте импорты и потенциально опасные вызовы включённого корпуса предварительно проверены; математический `eval` допускает только арифметическое дерево выражения.

## Протокол

1. Фиксируются байты всех решений и набора HumanEval+ v0.1.10 (`data/manifest.json`). Никакие решения не исправляются: синтаксические ошибки и ошибки загрузки остаются исходами измерения.
2. Выполняется проверка эталонных программ. На HumanEval/32 для входа `[9, -6, 20999, 2, 8, -4, -10, 26, 6, 5, -1, 8]` найденный эталоном корень не удовлетворяет допуску `1e-4`. Эта задача исключается из агрегатов. Контроль самосогласованности не доказывает, что все эталоны верны спецификациям.
3. Для каждой задачи дополнительные входы перемешиваются `random.Random(20261008 + task_number)`. Одна перестановка используется для обеих моделей и всех вложенных бюджетов. В этой работе не усреднялись результаты по многим перестановкам.
4. Вызовы выполняются с глубокими копиями аргументов. Сопоставление ответов соответствует HumanEval-ветви EvalPlus v0.3.1: точное сравнение либо численный допуск; для `find_zero` — остаток полинома. Для вещественных ответов нулевой допуск заменяется `1e-6`, `rtol=1e-7`.
5. Основной лимит одного вызова — `max(10 секунд, 4 × время эталона)`. Независимый поток контроля проверяет срок каждые 0.01 секунды. Операционный лимит всего процесса задачи — 180 секунд; в основном запуске он не сработал. Тестирование прекращается при первом отказе, его ранг сохранён. Входы после отказа не выполняются: их исход не нужен для критерия прохождения всего набора.
6. `analyze.py` вычисляет вложенные результаты по рангу первого отказа. Для каждой модели знаменатель равен 163. Логические ошибки и тайм-ауты указаны отдельно. Ошибки самого рабочего процесса не засчитываются как ошибки модели: анализ при них останавливается.

Пилот с лимитом `max(1 секунда, 4 × время эталона)` сохранён отдельно. У Code Llama число полностью принятых решений изменилось с 56 на 57, у GPT-4 базовое число — со 140 на 141, а полное осталось 134. Это чувствительность к времени, а не результат исправления программ.

## Состав

- `runner.py` — переносимый стенд повторного выполнения;
- `analyze.py` — агрегирование, таблица и CSV по задачам;
- `test_evaluator.py` — 10 проверок стенда и целостности данных;
- `data/` — неизменённые программы, сжатый набор и SHA-256;
- `results/final/` — основной реальный прогон с лимитом 10 секунд;
- `results/measured/` — пилотный прогон с лимитом 1 секунда;
- `results/control/` — контроль эталонных программ;
- `results/analysis/` — итоговые показатели и CSV;
- `results/pilot-analysis/` — показатели пилота;
- `PROVENANCE.md` — источники, лицензии и границы выводов.

## Как интерпретировать

Выводы относятся к двум фиксированным историческим корпусам и одному набору коротких Python-функций. Вклад работы — повторный запуск, проверка согласованности эталонов, разделение причин отказа и анализ вложенных тестовых бюджетов. Успешное прохождение конечного набора тестов не доказывает общую корректность программы. Отдельные входы не считаются независимыми наблюдениями; единица анализа — решение одной задачи.
